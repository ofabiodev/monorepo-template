# AGENTS.md

Instructions for AI coding agents working in this repository. Human-facing setup lives in `README.md`; this file is the working contract: commands, conventions, boundaries, and how to verify your work.

## Project overview

Monorepo template with two apps and a shared bun workspace root:

- `apps/web`: React 19 + Vite 8 + TanStack Router (file-based) + TanStack Query + Zustand/immer + Lingui v6 (i18n). Package name `@monorepo/web`.
- `apps/api`: Go 1.26 HTTP API using `net/http`, `pgx/v5`, `golang-migrate`, and `sqlc`.
- Infra: PostgreSQL 17, Docker Compose, Makefile as the single entry point.

The only frontend route today is `GET /` (home), which calls the API's `GET /hello` through `/api/hello`.

## Setup and commands

Always prefer the Makefile targets. Run `make help` to list them.

```bash
make install        # bun install (root lockfile) + go mod download
make up             # full stack in Docker: web :3000, api :8080, postgres :5432
make down           # stop the stack (keeps the db volume)
make dev-api        # postgres + migrations + Go API locally on :8080
make dev-web        # Vite dev server on :3000, proxies /api -> :8080
make lint           # biome check (web) + go vet (api)
make build          # web bundle + apps/api/bin/api
make test           # go test ./...
make sqlc           # regenerate apps/api/internal/repository
make migrate-up     # apply migrations (dockerized golang-migrate)
make migrate-down   # roll back the last migration
make migrate-create name=<snake_case>   # new *.up.sql / *.down.sql pair
```

Package manager is **bun only**. Never run `npm`, `pnpm`, or `yarn`, and never create a per-app lockfile. The only lockfile is the root `bun.lock`.

Go tooling: use `go tool sqlc` (pinned in `apps/api/go.mod`), not a globally installed `sqlc`.

Where new code goes:

- New page: `apps/web/src/pages/<segment>/index.tsx` using `createFileRoute`. The router plugin regenerates `route-tree.gen.ts` on `make dev-web` or `make build`; commit the regenerated file.
- New shared TS code used by more than one app: `packages/<name>` as a workspace package, consumed with `"@monorepo/<name>": "workspace:*"`. Do not reach into `apps/web/src` from another app.
- New HTTP endpoint: a method on `Server` in `apps/api/internal/server/`, registered in `Routes()` with a Go 1.22+ pattern such as `"GET /things/{id}"`.
- New table or query: migration first, then query file, then `make sqlc`, then use the generated `repository.Queries`.

## Frontend conventions (`apps/web`)

**Stack.** React 19, TanStack Router (file-based routes in `src/pages`, `routeToken: "layout"`), TanStack Query for server state, Zustand + immer for client state, Tailwind CSS v4 via `@tailwindcss/vite`, Phosphor icons, `clsx` + `tailwind-merge` via `cn()` in `src/lib/cn.ts`.

**Imports.** Use the `@/` alias for everything under `src/` (for example `@/lib/api`, `@/components/not-found`). Never use relative paths that climb out of the current folder.

**Routes.** Each route file exports `Route = createFileRoute("/path/")({ component })`. Data fetching happens with `useQuery`/`useMutation` inside the component, not in `useEffect`. Query keys are arrays, for example `["hello"]`. The default `staleTime` is set in `app.tsx`.

**Environment.** Read env vars only through `src/lib/env.ts`, which validates `import.meta.env` with a TypeBox schema. Add new `VITE_*` variables to that schema and to the `.env.*` files. Vite only exposes variables that start with `VITE_`.

**Validation.** Use TypeBox (`import { Type } from "typebox"`, `import { Value } from "typebox/value"`). Do not import from `@sinclair/typebox`; that package is not installed.

**Storage.** Persist values through `src/lib/storage.ts` (`getValidatedStorageItem` / `setStorageItem` with the keys in `storageKeys`). Do not call `localStorage` directly.

**State.** Global client state goes in `src/stores/<name>.ts` with `create` + `immer`. Keep server data in TanStack Query, not in stores.

**Styling.** Tailwind utility classes. Theme tokens (`bg-background`, `text-foreground`) come from `globals.css`.

**Formatting and lint.** Biome, configured in `apps/web/biome.json`: 2 spaces, double quotes, no semicolons, line width 80, `noConsole` as a warning, and a 600-line cap per file. `make lint` runs with `--error-on-warnings`, so warnings fail CI. Fix them, do not silence them.

**Generated files you must not edit by hand:** `src/route-tree.gen.ts`, `src/locales/*/messages.ts`.

## Internationalization (Lingui v6)

Supported locales: `en` (source language) and `pt-BR`. Defined in `apps/web/lingui.config.ts`.

### How it works

1. **Source strings are written in code** with macros. Macros are compile-time transforms, so they must come from the macro entry points:
   - JSX text: `import { Trans } from "@lingui/react/macro"` then `<Trans>Page not found</Trans>`.
   - Plain strings (attributes, props, arrays, logic): `import { t, msg } from "@lingui/core/macro"`, for example `t\`Loading...\`` or `msg\`Loading...\``.
   - Do not use `@lingui/macro`. It was removed; it has no v6 release and the code must not depend on it.
2. **Extraction** (`bun run i18n:extract`, which runs `lingui extract`) scans `src/` and writes or updates `src/locales/<locale>/messages.po`, adding new `msgid`s and marking removed ones.
3. **Translation** happens in the `.po` files. Fill `msgstr` for `pt-BR`. The `en` catalog maps each msgid to itself, so `msgstr` can be left empty in `en`.
4. **Compilation** (`bun run i18n:compile`, which runs `lingui compile --typescript`) generates `src/locales/<locale>/messages.ts`. These compiled files are committed, and you must never edit them by hand.
5. **Runtime.** `src/stores/locale.ts` picks the initial locale from localStorage (`app-locale`), falling back to the browser language (`pt*` gives `pt-BR`, `en*` gives `en`, anything else gives `en`). `setLocale()` lazily loads the compiled module through `import.meta.glob("../locales/*/messages.ts")`, calls `i18n.load` and `i18n.activate`, and persists the choice. `main.tsx` awaits this before the first render, so components never render without a loaded catalog.

### Rules for agents

- Every user-facing string in the UI must be wrapped in `<Trans>`, `t`, or `msg`. A hard-coded English string in TSX is a bug.
- Use `msg` for strings that are declared once and rendered later (constants, config arrays). Use `t` inside functions that run at render time.
- Interpolation uses named placeholders: `t\`Hello ${name}\`` (the macro turns this into ICU-style placeholders). Do not concatenate translated strings.
- Plurals use `plural` from the macro, not ternaries on a count.
- Do not translate API payloads. The API returns `{"message":"hello world"}` as-is; the frontend decides how to label it.
- After changing UI text: run `bun run i18n:extract`, fill the `pt-BR` `msgstr`, run `bun run i18n:compile`, and commit the `.po` and `.ts` files together.

### Known state

The catalogs still contain entries from the removed starter home page (`src/pages/_home/index.tsx` at lines 67, 85, 103, for example "4 minute read"). They are harmless, but the next `i18n:extract` will mark them obsolete. Clean them up deliberately, and do not mix that cleanup into unrelated changes.

## Backend conventions (`apps/api`)

**Stack.** Go 1.26 (`go.mod` pins `go 1.26`). `net/http` ServeMux with method patterns (no third-party router). `pgx/v5` pool (`pgxpool`). `golang-migrate` for schema. `sqlc` with `sql_package: pgx/v5` for typed queries. `slog` for logging. `godotenv/autoload` reads `apps/api/.env` if present.

**Configuration.** Read config only in `internal/config`. `DATABASE_URL` is required; `PORT` defaults to `8080`. Do not call `os.Getenv` from handlers or repository code.

**Startup and shutdown.** `main.go` wires config, then the DB pool (which pings the database and fails fast), then the HTTP server. It handles `SIGINT`/`SIGTERM` with a 10 second graceful shutdown. Keep that flow when you add dependencies.

**Handlers.** Put handlers on `*Server` in `internal/server`. Use the `writeJSON` helper for responses. Set `ReadHeaderTimeout` (already set on the server); do not create new `http.Server` values per request.

**Errors.** Wrap with context: `fmt.Errorf("doing X: %w", err)`. Return errors to `main` or to the handler's caller; do not `log.Fatal` outside `main`.

**Database and sqlc.** Schema changes flow in this order, and skipping a step breaks the build or the database:

1. `make migrate-create name=<what_it_does>` creates a sequential `NNNNNN_<name>.up.sql` and `.down.sql` pair in `apps/api/migrations/`.
2. Write the forward migration in `*.up.sql`, and the exact inverse in `*.down.sql`. Use `DROP ... IF EXISTS` in down files; that keeps re-running a rollback safe. sqlc reads both files from `migrations/`, so keep them valid SQL.
3. Write queries in `apps/api/queries/<area>.sql` with `-- name: GetThing :one` (or `:many`, `:exec`, `:execrows`).
4. Run `make sqlc`. It regenerates `internal/repository/`; commit the output.
5. Run `make migrate-up` locally and test the query.

Type mapping from `sqlc.yaml`: `uuid` becomes `uuid.UUID` (`*uuid.UUID` when nullable), and `timestamptz` becomes `time.Time` (`*time.Time` when nullable). Do not hand-edit `internal/repository`.

**Never edit an applied migration.** Once a migration has been merged or applied anywhere, add a new one instead. Editing it desynchronizes every database that already ran it.

**Tests.** No test files exist yet. When you add logic, add `_test.go` files next to the code. Use `httptest` for handlers. For repository tests, use a real Postgres (the compose database), not mocks.

## Docker and infrastructure

- `docker-compose.yml` services: `postgres` (healthcheck with `pg_isready`), `migrate` (runs `golang-migrate up` once, mounts `apps/api/migrations` read-only), `api` (starts only after `migrate` completes successfully), `web` (nginx, proxies `/api/` to `api:8080/`).
- Host ports are configurable with `POSTGRES_HOST_PORT`, `API_HOST_PORT`, and `WEB_HOST_PORT`. Keep the defaults at 5432, 8080, and 3000, and use the env vars when a port is busy. Do not hard-code other host ports.
- The compose database credentials (`app`/`app`) are local development values only. Do not reuse them for anything shared or deployed.
- The web Dockerfile builds from the repo root because it needs the root `package.json` and `bun.lock`. Keep `context: .` in compose for the `web` service.
- The api image is distroless `nonroot` and has no shell. Do not add `RUN` steps that expect a shell in the runtime stage.
- After touching any Dockerfile, compose file, or nginx config, validate with `docker compose config --quiet` and run `make up`, then `curl localhost:$API_HOST_PORT/hello` and `curl localhost:$WEB_HOST_PORT/api/hello`.

## Verification before you finish

Run the checks that match what you changed. Report what you ran and what the output was.

| You changed | Run |
|---|---|
| Any TS/TSX in `apps/web` | `make lint` and `make build` |
| UI strings | `bun run i18n:extract` and `bun run i18n:compile`, then `make build` |
| Go code | `make lint` (go vet), `make test`, `gofmt -l apps/api` must print nothing |
| Migrations or queries | `make sqlc`, `make migrate-up`, then `make build` |
| Dockerfiles, compose, nginx | `docker compose config --quiet`, then `make up` with a `curl` check |

Dev servers are not a substitute for these checks. If something cannot be run in your environment (for example, Docker is unavailable), say so explicitly instead of claiming it passes.

## Boundaries

**Always**

- Use `make` targets, bun, and `go tool sqlc` as documented above.
- Keep `route-tree.gen.ts`, `internal/repository/`, and compiled `messages.ts` in sync with their sources by regenerating them, never by editing them.
- Commit the root `bun.lock` alongside any `package.json` change.

**Ask first**

- Adding a dependency to either app, or upgrading a major version (especially Lingui, Vite, Tailwind, or Go). The Lingui SWC plugin has to stay compatible with the `@swc/core` runtime pulled in by `@vitejs/plugin-react-swc`; a mismatch breaks the build.
- Adding a new Go router or ORM, or replacing `pgx`.
- Changing the Docker base images or the Go version.
- Changing the API response shape of `GET /hello` or any other existing route.
- Deleting migrations or dropping columns, tables, or data.

**Never**

- Commit `.env` files, credentials, or anything under `node_modules/`, `dist/`, or `apps/api/bin/`.
- Edit an applied migration (see Backend conventions).
- Import `@sinclair/typebox`, call `localStorage` directly, or add `@lingui/macro`.
- Create `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, or per-app lockfiles.
- Hard-code translations, secrets, or environment-specific URLs in source files.

## Git and commits

- Use Conventional Commits: `feat(api): add GET /hello`, `fix(web): ...`, `chore(infra): ...`, `docs: ...`. The scope is `web`, `api`, `infra`, or omitted for root changes.
- Keep a commit to one concern. A schema change, its `make sqlc` output, and the query that uses it belong in the same commit. Translation updates (`.po` plus compiled `.ts`) belong with the UI change that caused them.
- Do not rewrite history on shared branches. Do not use `--no-verify`.

## Common pitfalls

- **Port already in use.** Another project on the host may hold 5432 or 8080. Override with env vars instead of killing the process.
- **`make dev-web` cannot reach the API.** The Vite proxy targets `localhost:8080` fixed in `vite.config.ts`. If you run the API elsewhere, change that target and keep `VITE_API_URL=/api`.
- **`route-tree.gen.ts` changed after a build.** That is expected when routes change. Commit it.
- **`make sqlc` fails after a schema change.** Read the error for the file and line first. Check that the migration is valid SQL and that every query references existing tables and columns. Run `make sqlc` after each migration rather than batching several.
- **`go run` reads the wrong config.** `godotenv/autoload` reads `.env` from the current working directory. Run `make dev-api` from the repo root, or `cd apps/api` first.
- **Lingui strings missing in the UI.** The string was not wrapped in a macro, or the locale was not compiled. Run `i18n:extract` and `i18n:compile`.
